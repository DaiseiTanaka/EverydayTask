# 包括的コードレビュー＆リファクタリング

**重要: 修正は既存影響のないよう慎重に行うこと。**

## 引数の解釈

`$ARGUMENTS` を解析し、以下のルールで実行対象を決定する:

| 引数パターン | 実行内容 |
|-------------|---------|
| (空) | 全観点で `git diff HEAD~1` の差分全体をレビュー |
| `safety` | データ安全性のみ |
| `consistency` | 機能の統一性・整合性のみ |
| `design` | 設計（MVVM & クリーンアーキテクチャ）のみ |
| `quality` | コード品質のみ |
| `ui` | デザイン・UI のみ |
| `safety src/Service/` | データ安全性を指定パスに限定してレビュー |
| `src/Service/` (パスのみ) | 全観点を指定パスに限定してレビュー |

**観点キーワードは先頭の1語で判定する。** 残りの引数は対象パスとして扱う。

---

## ステップ1: 差分と影響範囲の把握

1. `git diff HEAD~1 --stat` で変更ファイル一覧を取得（対象パスが指定されている場合はそのパスに限定）
2. 変更されたファイルをすべて読み込む
3. 変更ファイルから参照・依存されているファイルも特定して読み込む
4. 影響範囲マップを作成する

---

## ステップ2: 観点別チェック

引数で観点が指定されている場合、該当する観点ファイルを **Read ツールで読み込んで** その内容に従いチェックを実施する。
観点が指定されていない場合（全観点）は、**すべての観点ファイルを読み込んで** 全チェックを実施する。

| 観点キーワード | 読み込むファイル |
|--------------|----------------|
| `safety` | `.claude/skills/refact/perspectives/safety.md` |
| `consistency` | `.claude/skills/refact/perspectives/consistency.md` |
| `design` | `.claude/skills/refact/perspectives/design.md` |
| `quality` | `.claude/skills/refact/perspectives/quality.md` |
| `ui` | `.claude/skills/refact/perspectives/ui.md` |

**全観点の場合は Agent ツールで観点ごとに並行レビューを実行し、効率化する。**

---

## ステップ3: 問題の分類と報告

発見した問題を以下の優先度で分類して報告する:

| 優先度 | 分類 | 説明 |
|--------|------|------|
| P0 | Critical | データ消失リスク、クラッシュ、セキュリティ |
| P1 | High | デグレ、機能不全、設計違反 |
| P2 | Medium | コード品質、命名、アクセス修飾子 |
| P3 | Low | 最適化、リファクタリング提案 |

報告フォーマット:
```
### [P0/P1/P2/P3] 問題タイトル
- **ファイル**: path/to/file.swift:行番号
- **問題**: 問題の説明
- **影響**: 影響範囲の説明
- **修正案**: 具体的な修正内容
```

---

## ステップ4: 修正の実施

1. P0 → P1 → P2 の順に修正を行う（P3は報告のみ、修正はユーザー確認後）
2. **修正前に必ず影響範囲を再確認**する
3. 1つの修正ごとに、関連するテストやビルドへの影響を確認する
4. 既存の動作を壊さないことを最優先とする
5. 修正が大きい場合はユーザーに確認を取ってから実施する

---

## ステップ5: 知見の蓄積

レビューで発見した **新しいパターンの問題**（既存の観点ファイルに記載されていない問題）があれば、該当する観点ファイルの「過去のレビューで発見された典型的な問題」セクションに追記する。

蓄積の基準:
- 同じ問題が再発しうるパターンであること
- プロジェクト固有の知見であること（一般的な Swift のベストプラクティスは除外）
- 具体的な再発防止策が記述できること

蓄積のフォーマット:
```
- **問題の要約**: 具体的な状況と、なぜ問題なのか。修正方法または予防策
```

また、CLAUDE.md の Coding Rules に追加すべきルール（例: 新しい共通コンポーネントの使用ルール）があれば、CLAUDE.md にも反映する。

---

## ステップ6: 最終サマリ

すべての確認・修正が完了したら、以下のサマリを出力する:

```
## レビューサマリ

### 確認済みチェック項目
- [ ] 機能の統一性・整合性
- [ ] 設計（MVVM & クリーンアーキテクチャ）
- [ ] コード品質
- [ ] デザイン・UI
- [ ] データ安全性・パフォーマンス

### 発見した問題
| 優先度 | 件数 | 修正済み | 未修正 |
|--------|------|----------|--------|
| P0     |      |          |        |
| P1     |      |          |        |
| P2     |      |          |        |
| P3     |      |          |        |

### 修正内容の一覧
（修正したファイルと変更内容の概要）

### 残課題・推奨事項
（P3の提案や、ユーザー確認が必要な事項）
```
