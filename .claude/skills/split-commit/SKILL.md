# コミット分割＆プッシュ

現在の未コミット差分を論理的な単位に分割してコミットする。

---

## ステップ1: 差分の把握

1. `git status` で未コミット・未追跡ファイルを一覧取得
2. `git diff --stat` でファイルごとの変更量を把握
3. `git diff` で差分の内容を確認
4. `git log --oneline -5` で直近のコミットメッセージスタイルを確認

---

## ステップ2: コミット分割の提案

差分を分析し、以下の基準でコミット単位を決定する:

### 分割の基準

| 優先度 | 基準 | 例 |
|--------|------|-----|
| 1 | 機能単位 | 新機能の追加、既存機能の変更 |
| 2 | リファクタリング | 定数の集約、共通化、ファイル分離 |
| 3 | ローカライズ | `String(localized:)` への統一 |
| 4 | UI/UX 改善 | Dynamic Type 対応、タップ領域拡大 |
| 5 | バグ修正 | ロジックの修正、エッジケース対応 |

### 分割のルール

- **1コミット = 1つの論理的な変更** を原則とする
- 依存関係がある変更は依存される側を先にコミットする（例: 定数定義 → 定数参照）
- 同一ファイルに複数コミットの変更が混在する場合は `git add -p` でハンク単位でステージングする
- コミット数は 3〜7 を目安とし、過剰な分割は避ける

### コミットメッセージの規約

プロジェクトの既存コミットメッセージスタイルに従う。一般的な Conventional Commits 形式:

```
<type>: <description>

type: feat, fix, refactor, docs, style, test, chore
```

### 提案フォーマット

以下の形式でコミット分割案を提示する:

```
## コミット分割案

### コミット1: <type>: <description>
- file1.swift（変更内容の概要）
- file2.swift（変更内容の概要）

### コミット2: <type>: <description>
- file3.swift（変更内容の概要）
...
```

**ユーザーに提示して承認を得る。承認が得られるまでコミットを実行しない。**

ただし、ユーザーが引数やメッセージで「そのまま進めて」「go」等と指示した場合は承認をスキップして実行する。

---

## ステップ3: コミットの実行

承認された分割案に従い、以下の手順でコミットを作成する:

### 3-1. ステージング戦略

| ケース | 方法 |
|--------|------|
| ファイル全体が1コミットに属する | `git add <file>` |
| ファイル内に複数コミットの変更が混在 | `git add -p <file>` でハンク単位選択 |
| ハンク分割が困難 | ファイルを一時コピー → 該当変更のみ適用 → ステージ → 復元 |

### 3-2. コミット作成

```bash
git commit -m "$(cat <<'EOF'
<commit message>

Co-Authored-By: Claude Opus 4.6 (1M context) <noreply@anthropic.com>
EOF
)"
```

### 3-3. 検証

- 全コミット完了後に最終的なビルドが通ることを確認（中間コミットはビルドが通らなくてもOK）
- `git log --oneline` で分割結果を確認

---

## ステップ4: プッシュ

引数に `push` が含まれている場合、またはユーザーがプッシュを指示した場合:

```bash
git push
```

プッシュ前にリモートとの差分を確認し、force push が必要な場合はユーザーに確認を取る。

---

## ステップ5: 結果報告

```
## コミット分割完了

| # | ハッシュ | メッセージ | ファイル数 |
|---|---------|-----------|----------|
| 1 | abc1234 | refactor: ... | N files |
| 2 | def5678 | feat: ... | N files |
...

プッシュ: ✅ 完了 / ⏸ 未実行
```
